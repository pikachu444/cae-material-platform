## P1. Catalog Schema Bundle - JSON 한 파일로 DB 구조 일괄 정의·발행

### 목표

운영 조직이 이미 보유한 JSON Schema(draft 2020-12 + `x-` 확장) 세트를 번들 매니페스트와 함께 업로드하면 `Database/Profile/Table/Attribute/LinkType`이 한 번에 생성·검증·발행되도록 한다. 재실행 시 멱등(upsert-by-key)이어야 한다.

### 배경(현재 상태)

- 카탈로그 구조는 `POST /api/v1/catalog/tables`, `/tables/{id}/attributes`, `/link-types`, `/catalog/publication:validate|:publish`로 하나씩만 만들 수 있다(`backend/src/cmp/modules/catalog/adapters/api/configurable.py`).
- 유일한 일괄 세팅 수단은 명령형 시딩 스크립트 `scripts/seed_full_demo.py`이며, 여기에 이미 멱등 upsert 패턴(`_find_by_content -> create-or-revise`)과 의존 순서 관리가 구현돼 있다. 이 패턴을 재사용한다.
- `x-` 확장 키워드를 해석하는 코드는 저장소에 없다.

### 입력 형식

- 번들 매니페스트: `document_type: "cmp.catalog-schema-bundle"`, `schema_version`, `bundle_id`, `bundle_version`, `database{key,name}`, `profile{key,name}`, `tables[]{key,name,record_schema_ref,folder_tree[],description}`, `link_types[]{key,source_table,target_table,forward/reverse_label,cardinalities,derived_from}`, `unit_profiles[]`, `import_policy{conflict_strategy,publish,dry_run_default,delete_missing:false}`
- 레코드 스키마: JSON Schema draft 2020-12. 그룹 객체 아래 속성을 정의하며 확장 키워드는 아래 매핑 표를 따른다.
- 픽스처: 요청자가 매니페스트 1개 + 레코드 스키마 6개(`technical-data`, `tensile-test`, `dma-test`, `fld-test`, `elastoplasticity`, `statistics`)를 제공한다. 이를 계약 예제(`contracts/examples/`)와 테스트 픽스처로 사용한다.

### `x-` 확장 -> 카탈로그 매핑 규칙

| 스키마 요소 | 카탈로그 대응 |
| --- | --- |
| 파일당 `x-table-key` | Table key(1:1) |
| 그룹 객체명 | Layout 그룹 |
| 속성의 `x-key` | Attribute key(필수, `^[a-z][a-z0-9_]{0,63}$` 검증) |
| `type:number` + `x-unit`(+ `x-quantity`) | `data_type:number`, `normalized_unit`, `quantity_semantics` |
| `x-discrete` | `data_type:discrete` + `allowed_values`; `x-discrete-open`은 text + 제안값 메타 |
| `format:date` | `data_type:date` |
| `x-business-key:true` | 해당 속성 값을 Record `external_key`로 승격하는 규칙 등록 |
| `x-reference{schema_key,pointer}` | `data_type:record_reference`(+ `reference_table_id`) 및 매니페스트 `link_types[].derived_from`과 대조 검증 |
| `x-curve{...}` | `data_type:curve` + 채널 메타데이터(P2 선행 시 저장, 아니면 스키마 원문 보존) |
| `x-indexed` / `x-searchable` | 1차 구현에서는 스키마 원문에 보존만 하고 동작 없음(후속 논의) |

### 작업

1. `contracts/catalog/catalog-schema-bundle.schema.json` 신설 - 매니페스트와 확장 키워드의 계약. 계약 검증 테스트(`tests/contracts/`)에 positive/negative 예제 포함.
2. `POST /api/v1/catalog/schema-bundles:plan` - 번들을 받아 dry-run 계획 보고서를 반환: 생성/개정/변경없음/오류 항목별 목록(테이블·속성·링크타입 단위), 의존 순서, 발행 대상 revision 목록. DB 변경 없음.
3. `POST /api/v1/catalog/schema-bundles:apply` - 계획 실행. `Database -> Profile -> Table -> Attribute -> Layout -> LinkType` 순서로 upsert(기존 key의 내용 비교 후 동일하면 skip, 다르면 새 revision)한 뒤 `publication:publish`를 대상 전체에 순차 적용. 실패 시 이미 발행된 항목 목록과 미완료 항목을 담은 문제 보고를 반환한다(부분 성공 상태를 숨기지 않는다).
4. 원본 번들 파일(매니페스트+스키마)을 immutable artifact로 보존하고 각 생성물 revision의 `change_reason`에 `bundle_id@bundle_version`을 기록한다.
5. 번들 export - `GET /api/v1/catalog/schema-bundles:export?database=<key>`로 현재 발행 구조를 동일 형식으로 역직렬화한다(왕복 가능성 확보).
6. Administration UI에 번들 업로드(계획 미리보기 -> 적용) 화면 1개를 추가한다.
7. `x-business-key` 승격 규칙: 레코드 등록/수정 시 해당 속성 값을 `external_key`에 복사하고 중복 시 기존 트리거 오류를 그대로 노출한다.

### 완료 기준

- 제공된 픽스처 번들을 신규 DB에 `:plan -> :apply`하면 Table 6개, LinkType 6개가 발행되고 같은 번들 재적용 시 변경 0건으로 종료된다.
- 스키마 하나의 속성을 수정한 번들 재적용 시 해당 Attribute만 새 revision으로 발행된다.
- 잘못된 번들(`x-key` 누락, 참조 대상 테이블 부재, cardinality 모순)은 `:plan` 단계에서 항목별 오류로 거부된다.
- export 결과를 다시 `:plan`에 넣으면 변경 0건이다(왕복성).
- 계약 테스트/통합 테스트(PostgreSQL 게이트) 통과, `docs/admin-guide`에 사용 절차 1절 추가.

### 제외 범위

- `x-indexed`/`x-searchable`의 실제 인덱스 생성(후속)
- 레코드 데이터 import(기존 경로 사용)
- 스키마 삭제(`delete_missing`은 항상 `false`)

## P2. 곡선(Curve) 채널 메타데이터와 편차 채널

### 목표

카탈로그 curve 속성이 "무엇의 곡선인지"(x/y/보조 채널의 물리량·단위·스케일, 선택적 편차 채널)를 정의·저장하고 조회 API와 화면이 이를 사용해 축·단위·오차대를 표시하도록 한다.

### 배경

- 현재 curve 값은 `artifact_id + sha256` 포인터뿐이며 채널 메타가 없다(`backend/migrations/versions/20260825_059_T49_configurable_catalog.py`의 `record_curve_value`, `api/records.py:120-127`).
- 구조적 채널 개념은 별도 파이프라인(`contracts/datasets/canonical-test-data.schema.json`의 Channel: `quantity_semantics/axis_role/단위/정규화`)에만 존재한다. 편차(deviation) 채널 개념은 저장소 전체에 없다.

### 작업

1. Attribute 정의(`AttributeDefinitionContent`)에 curve 전용 메타 추가: `curve_channels[]{role: x|y|series|deviation, quantity_semantics, normalized_unit, scale: linear|log10}`. 마이그레이션을 포함하고 기존 데이터에 영향이 없어야 한다.
2. curve 값 등록 시 artifact 내용의 채널 헤더가 Attribute 정의와 일치하는지 검증한다(불일치 시 항목별 오류).
3. 곡선 artifact의 표준 포맷을 명시한다. `canonical-test-data`의 Channel 표현을 재사용한 단일 문서 또는 Parquet 컬럼 규약 중 하나를 택하고 계약으로 고정한다.
4. 조회 API에 채널 메타를 포함하고 Materials 상세 곡선 화면에서 축 라벨·단위·(있으면) 평균 ± 편차 밴드를 렌더링한다.
5. P1의 `x-curve{x_pointer,y_pointer,series_pointer,deviation_pointer,단위,스케일}`을 이 메타로 저장하도록 연결한다.

### 완료 기준

- 편차 채널을 가진 통계 대표 곡선(`statistics` 픽스처)이 등록·조회·표시(오차대)까지 동작한다.
- 채널 불일치 artifact는 등록이 거부되고 원인 항목이 보고된다.
- 기존 curve 레코드는 메타 없음 상태로 계속 조회할 수 있다(후방 호환).

### 제외 범위

- 곡선 편집기
- 다축(2y) 차트
- 채널 수 5개 초과

## P3. 단위 시스템 확장과 단위 프로파일

### 목표

CAE 실무 단위계(mm-tonne-s: MPa, tonne/mm³ 등)와 온도를 포함한 단위 정규화·표시 변환을 지원하고 "단위 프로파일"(조직 기본 표시 단위 묶음)을 정의할 수 있게 한다.

### 배경

- 환산표가 13쌍 하드코딩(`backend/src/cmp/modules/catalog/domain/registration-unit-mappings.json`)이고 온도 환산·차원 검증·파생 단위가 없다. 미등록 단위는 `ValueError`다.
- Export 단위계는 `kg_m_s` 단일 하드코딩(`exporting/domain/neutral_hyperelastic.py:21-24`)이다. -> P6과 연동.
- 운영 조직 데이터에는 `tonne/mm3`(소재 밀도)와 `kg/m3`(시뮬레이션 데이터)가 혼재한다.

### 작업

1. 단위 처리 계층을 도입한다. 차원 검증 + 환산이 가능한 라이브러리(예: Pint) 채택 또는 매핑 테이블의 체계적 확장(질량/길이/시간/온도/파생: 응력, 밀도, 속도, 주파수, 에너지). 선택 근거를 ADR로 기록한다.
2. 최소 지원 단위 목록(수용 기준): `MPa/GPa/kPa/Pa`, `tonne/mm3 <-> kg/m3 <-> g/cm3`, `mm/min <-> mm/s <-> m/s`, `degC <-> K`, `Hz`, `N`, `% <-> 1`, `mm/cm/m`.
3. `unit_profiles` 리소스(P1 매니페스트의 `unit_profiles`와 동일 형식): 조직/프로젝트별 기본 표시 단위 묶음. 조회 API가 프로파일 기준 표시값을 함께 반환한다.
4. 잘못된 차원 조합(예: 응력 속성에 밀도 단위)은 등록 시 거부한다.
5. 기존 13쌍 매핑과의 후방 호환 및 마이그레이션 불필요를 확인한다.

### 완료 기준

- `technical-data` 픽스처(밀도 `tonne/mm3`)와 `elastoplasticity` 픽스처(밀도 `kg/m3`)가 모두 등록되고 동일 물리량으로 상호 표시 변환된다.
- `degC` 입력이 정규화 저장되고 표시 프로파일에 따라 `degC/K`로 조회된다.
- 차원 불일치 등록이 항목별 오류로 거부된다.

### 제외 범위

- Export 카드의 단위계 변환(P6에서 수행)
- UCUM 전 어휘 지원
- 화면 단위 전환 토글 UI(후속)

## P4. 시험 종류별 Test Data 커버리지 확장(DMA·FLD 우선)

### 목표

인장 이외의 시험 데이터가 "원천 업로드 -> 중립 저장 -> (해당 시) 프로세싱 연결"의 동일한 governed 경로를 타도록 시험 종류별 `test-data` 프로파일을 확장한다. 1차 대상은 DMA 주파수-온도 스윕과 FLD다.

### 배경

- Canonical Test Data JSON(`contracts/datasets/canonical-test-data.schema.json`)은 채널 2-512개의 범용 구조라 DMA/FLD도 담을 수 있지만, governed tabular import의 `data_schema` enum은 `monotonic_tension|monotonic_compression|planar_tension|biaxial_tension|simple_shear|shear_relaxation` 6종뿐이다(`contracts/datasets/governed-import-resources.schema.json`).
- 중립 데이터는 시험별이 아니라 모델 패밀리 3종(`oneOf`) 기준의 단일 봉투다(`contracts/modeling/neutral-material.schema.json`). DMA는 `shear_relaxation` Dataset으로 우회 중이고 FLD는 대응 개념이 없다.
- Prony/DMA 피팅 자체는 구현돼 있다(`processing/domain/polymer_viscoelastic.py`의 storage+loss 동시 피팅, `viscoelastic_master_curve.py`).

### 작업

1. governed import `data_schema`에 `dma_frequency_temperature_sweep`, `dma_strain_sweep`, `forming_limit`를 추가한다. 필수 채널 정의: DMA sweep = `temperature|frequency`(independent) + `storage_modulus + loss_modulus`(dependent, 선택 `tan_delta`), FLD = `minor_strain`(independent) + `major_strain`(dependent).
2. 각 신설 `data_schema`의 Import Profile 검증 규칙(단위 allowlist, 채널 수, 단조성 요구 없음)을 계약과 코드에 추가한다.
3. Modeling -> Data 화면에서 신설 시험 종류 선택·미리보기를 지원한다.
4. DMA sweep Dataset -> 기존 `polymer.dma_prony_fit_compare` / master curve 처리로 연결되는 exact-revision 경로를 문서화하고 통합 테스트로 고정한다.
5. FLD는 처리 없이 저장·조회·카탈로그 레코드 연결(P1 `fld_test` 테이블)만 보장한다. "프로세싱 대상이 아닌 시험 데이터도 1급 시민"임을 수용 기준으로 명시한다.
6. 시험별 중립 표현이 필요한 경우(예: DMA 마스터커브) `cmp.neutral-material`의 `curve_stages` / `extensions`를 사용하는 규칙을 `docs/domain`에 1절로 문서화한다(스키마 개정 없이).

### 완료 기준

- DMA 스윕 CSV와 FLD CSV가 governed import로 등록되고 각 Dataset revision이 카탈로그 레코드(`dmatest`/`fldtest`)와 링크된다.
- DMA Dataset에서 Prony 피팅 -> LinearViscoelastic IR -> 카드 미리보기까지 기존 경로가 끊기지 않는다.
- 계약 positive/negative 예제와 PostgreSQL 통합 테스트를 추가한다.

### 제외 범위

- 신규 재료 모델 추가(#195/#196 범위 침범 금지)
- Creep/Fatigue/Adhesive/Dielectric(동일 패턴 후속)
- FLD 기반 성형 해석 기능

## P5. 다수 시편 통계: 분포 피팅과 대표 Envelope 곡선

### 목표

같은 조건의 시편 그룹에서 (a) 스칼라 특성값의 분포 피팅(Normal/Weibull/Lognormal)과 (b) 곡선의 평균/상위 5%/하위 5% envelope 대표 곡선을 생성하고 이를 승인 가능한 대표 데이터 revision으로 보존한다.

### 배경

- 현재 통계는 평균/표본 SD/CV/중앙값/MAD/IQR/평균 95% CI와 이상치 검출(modified z-score)+사람 판정까지다(`statistics/domain/reference_tensile_replicates.py`, `processing/domain/common_ensemble.py`). 분포 피팅과 분위수 envelope(`p5/p95`)는 없다. `q1/q3`·평균 CI와 개념이 다름에 유의한다.
- 요구사항 문서(`docs/analysis/scatter-statistics.md`)에 산포 통계 요구가 이미 정리돼 있다.

### 작업

1. 스칼라 분포 피팅 메서드 추가: 대상 특성값(예: proof stress, tensile strength) 그룹에 Normal/Weibull(2p)/Lognormal MLE 피팅, 적합도 지표(AD 또는 KS 통계, log-likelihood) 보고. 모델 자동 추천은 하되 선택은 사람이 하며 선택 사유가 필수다(기존 `selection_mode` 패턴 재사용).
2. 곡선 envelope 메서드 추가(`curves.envelope_quantile`): 공통 그리드 정렬(기존 `curves.align_linear_intersection` 재사용) 후 점별 `mean/p05/p95`(+표본 SD) 곡선 산출. 분위수 계산 방식(경험적/정규가정)을 명시 파라미터로 둔다.
3. 결과를 대표 데이터 revision(불변)으로 저장: 소스 시편 exact revision 목록 + 제외 시편과 사유(기존 Assessment 재사용) + 레시피 고정.
4. 대표 데이터의 리뷰·승인 경로를 연결한다(기존 review/release 재사용, aggregate type 확장).
5. Fit 단계 입력으로 "개별 시편" 대신 "대표 곡선"을 선택할 수 있게 한다.
6. `contracts/statistics/`에 분포·envelope 리소스 스키마를 추가하고 결정적 synthetic 픽스처와 parameter-recovery 테스트를 추가한다(#158 3A 패턴).

### 완료 기준

- 시편 5개 픽스처에서 `mean/p05/p95` 곡선과 Weibull 피팅 결과가 결정적으로 재현된다(시드 고정).
- 대표 곡선 revision이 승인 후 Fit 입력으로 선택 가능하다.
- 이상치로 제외된 시편이 대표값 계산에서 빠지고 그 사실이 계보에 남는다.

### 제외 범위

- A-basis/B-basis 등 규격 특성값(후속)
- 3모수 Weibull
- 곡선 함수형 PCA

## P6. 솔버 카드 템플릿 시스템(Template Designer) 및 대상 솔버·단위계 확장

### 목표

코드 수정 없이 신규 솔버 카드 형식을 추가할 수 있는 템플릿 + 매핑 프리셋 체계를 도입하고 LS-DYNA를 1차 검증 대상으로 추가한다. 카드 출력 단위계(kg-m-s 외 mm-t-s 등)를 선택 가능하게 한다.

### 배경

- 현재 카드 생성은 Python f-string 하드코딩이다(`exporting/domain/reference_isotropic_tabulated_plasticity.py:522-559` 등). Jinja2/템플릿 파일은 0건이다. 지원 솔버는 Abaqus·OpenRadioss 2종, 단위계는 `kg_m_s` 상수(`neutral_hyperelastic.py:21-24`)다.
- 반면 입력 측에는 이미 데이터 주도 구성이 있다: Mapping Profile(Process), Scientific Profile(Fit, 승인 상태 포함). Export만 코드에 갇혀 있다.
- 플러그인 계약에 `solver_exporter` 확장 타입이 예약돼 있으나 실 구현·결선이 없다(`contracts/plugins/plugin-manifest.schema.json`, `adr/0004`).
- 기존 Mapping Report(`exact/transformed/approximated/unsupported`)와 `preview -> delivery` digest 검증은 유지 가치가 높다.

### 작업

1. 경로 결정(ADR): (a) 코어에 governed 템플릿 리소스(Jinja2 sandbox) 도입 vs (b) `solver_exporter` 플러그인 1급 결선. 권장: (a)를 기본으로 하되 렌더러를 플러그인 경계 뒤에 두어 (b)로 자연 확장한다.
2. Card Template 리소스: `template_id + revision`, 대상(`solver`, `solver_version`, `material_model`, `unit_system`), 템플릿 본문(placeholder 문법), 필요한 IR 경로 선언 목록, `draft -> publish` 라이프사이클(기존 revision 커널 재사용).
3. Mapping Preset 리소스: IR/Neutral 경로 -> 템플릿 placeholder 바인딩 + 단위 변환 지시(P3 계층 사용) + 상수/서식(유효숫자, 컬럼 폭). 렌더 시 Mapping Report를 기존 형식으로 자동 생성한다. 바인딩 안 된 placeholder는 `unsupported`로 보고하고 `exportable=false`로 둔다.
4. 렌더 파이프라인: 선택 모델 revision + 템플릿 revision + 프리셋 revision을 exact 고정 -> preview -> delivery(digest 검증 유지). 카드 헤더 주석에 세 revision ID를 기록한다.
5. 1차 템플릿 검증 세트: 기존 Abaqus `*PLASTIC` 카드와 OpenRadioss LAW36을 템플릿으로 재구현해 기존 하드코딩 출력과 바이트 동일함을 테스트로 증명한다. 이후 LS-DYNA `*MAT_024`(tabulated) 템플릿을 추가한다.
6. 단위계: 템플릿 대상의 `unit_system`을 P3 프로파일과 연결하고 mm-t-s 출력을 검증한다(밀도 tonne/mm³, 응력 MPa 환산).
7. Template Designer UI(Administration): 템플릿 편집·placeholder 목록·프리뷰(승인된 synthetic 모델로)·발행.

### 완료 기준

- 신규 솔버 카드 1종(LS-DYNA `MAT_024`)이 코드 배포 없이 템플릿+프리셋 등록만으로 미리보기·다운로드된다.
- 기존 Abaqus/OpenRadioss 경로가 템플릿 기반으로 전환된 뒤에도 기존 픽스처와 출력이 동일하다.
- mm-t-s 단위계 카드에서 밀도·응력·곡선 값의 환산이 검증된다.
- 템플릿·프리셋·카드가 exact revision으로 상호 고정돼 계보 조회가 된다.

### 제외 범위

- Optistruct/Ansys 템플릿(조직이 후속 기여)
- 솔버 실행 검증(virtual specimen 후속)
- 템플릿 마켓/서명 배포

## P7. 업로드 승인 워크플로와 역할 프리셋 정합

### 목표

(a) 시험 데이터/카탈로그 레코드 업로드가 "제출 -> 검토 -> 승인/반려" 큐를 거치도록 리뷰 대상을 확장하고, (b) 제품 역할 프리셋을 조직에서 조정 가능하게 한다.

- 일반 사용자 = 조회/다운로드/업로드 요청
- 데이터 매니저(신설) = 업로드 승인·프로세싱·대표값 승인
- 관리자 = 스키마·권한

### 배경

- 리뷰 백엔드는 임의 `aggregate_type`을 수용하지만 UI가 제출하는 대상은 `catalog.material`, `exporting.solver_card`, `exporting.neutral_solver_card` 3종뿐이다(`apps/web/src/review-request-action.tsx:7`). 시험 데이터/Record/Dataset 승인 큐가 없다.
- 제품 역할 preset은 3종 고정이고 API가 요청의 `featuregrants`를 무시하고 preset을 강제한다(`identity_access/domain/authorization.py:120-141`, `application/authorization.py:837`). `user` preset에 `processing.calibration`이 고정 포함되고 `testing.write`가 없어 "업로드만 하는 일반 사용자"와 "시험 Run 생성"이 동시에 성립하지 않는다.
- 14개 내부 role의 부여 서비스(`RoleBindingAdministrationService`)는 있으나 HTTP 라우터가 조립되지 않았다.

### 작업

1. 리뷰 대상 확장: `datasets.test_data_document`, `catalog.record`(또는 Domain Binding 단위)를 리뷰 요청 가능 aggregate로 UI·서비스에 결선한다. Activity 큐에 "업로드 승인" 유형을 표시한다.
2. "제출 시 검토 요청" 정책 플래그: 테이블/데이터셋 단위로 `requires_review_on_submit` 설정(기본 `false`, 기존 동작 유지).
3. ProductRole 프리셋 개편: `data_manager` 프리셋 신설(`processing.calibration + model.approval + catalog.edit + testing.write`) 및 `user` 프리셋에서 `processing.calibration` 분리 여부를 조직 설정으로 선택 가능하게 한다(기본값은 현행 유지, 설정은 `identity.manage` 권한자만).
4. 일반 사용자 업로드 경로 정비: 업로드 요청 시 Test Run/Specimen 자동 생성(사용자에게 `testing.write`를 주지 않고 서비스 계정 위임) 또는 user에 `testing.write` 선택 부여 중 하나를 ADR로 결정한다.
5. `RoleBindingAdministrationService` HTTP API를 조립하고 product-access 화면에 내부 role을 표시한다. DB 직접 INSERT 없이 세밀한 권한 운영이 가능해야 한다.
6. 프런트 role 게이팅: `/administration/*` 진입을 `product_role` 기준으로 숨김/안내한다(서버 403 의존 제거).

### 완료 기준

- 일반 사용자가 업로드 제출 -> 데이터 매니저 Activity 큐에서 승인 -> 레코드가 공개 검색에 노출되는 E2E가 통과한다(반려 시 새 revision 재제출 포함).
- SoD(작성자 자기승인 금지)와 exact revision 고정이 업로드 리뷰에도 적용된다.
- `data_manager` 프리셋 사용자의 스키마 편집은 거부되고(403) 승인·프로세싱은 허용된다.

### 제외 범위

- 다단계 승인 매트릭스/전자서명(후속 P11 후보)
- IdP 그룹 자동 매핑 UI

## P8. 웹 UI 로그인(OIDC Authorization Code + PKCE)

### 목표

실제 IdP(`CMP_OIDC_*`)가 설정된 배포에서 웹 UI가 표준 로그인으로 세션을 획득하게 한다. ADR-0034 결정 #3("normal deployments use a standard login")의 이행이다.

### 배경

- 백엔드는 RFC 9068 OIDC resource server가 완성돼 있고 fail-closed다(`backend/src/cmp/bootstrap/security.py:44-78`, `identity_access/adapters/oidc/pyjwt.py`).
- SPA의 유일한 세션 부트스트랩은 인증 없는 데모 토큰 라우트다(`apps/web/src/app.tsx:843-875`, `api.ts:1256-1270`). 실제 IdP 설정 시 UI가 토큰을 얻을 방법이 없다. `.env.example`에 `CMP_OIDC_*` 변수도 없다.

### 작업

1. SPA에 OIDC Authorization Code + PKCE 로그인: 로그인 진입/redirect 처리/silent refresh 또는 만료 재로그인/로그아웃. IdP 메타데이터(discovery) 기반 설정.
2. 배포 설정 노출: `VITE_CMP_OIDC_*`(`authority`, `client_id`, `scopes`) + `.env.example` 갱신(`CMP_OIDC_*` 서버 변수 포함).
3. 데모 모드(`CMP_DEMO_IDENTITY=true`)에서는 기존 자동 세션을 유지한다. 두 경로의 분기를 명시하고 데모 변수와 OIDC 변수 동시 설정 시 기동 거부하는 기존 동작을 유지한다.
4. 401/토큰 만료 시 사용자 안내와 재인증 흐름, `GET /api/v1/me` 기반 역할 표시.
5. 운영 가드: `CMP_ENVIRONMENT=production && CMP_DEMO_IDENTITY=true` 조합을 기동 거부한다.

### 완료 기준

- Keycloak(또는 임의 표준 OIDC IdP) 대상 E2E: 로그인 -> Materials 조회 -> 권한별 메뉴 노출 -> 로그아웃.
- 데모 compose 경로는 기존과 동일하게 무설정 동작한다.
- 토큰 미보유·만료·권한 부족의 3개 상태가 각각 구분된 UI 안내를 가진다.

### 제외 범위

- IdP 프로비저닝 자동화
- MFA(IdP 위임)
- 세션 공유 SSO 포털

## P10. 프로세싱 보강: Toe 보정(+선택: 전역 최적화 어댑터)

### 목표

인장 곡선 toe 구간 보정 메서드를 공통 파이프라인에 추가한다. 선택적으로 피팅 최적화기에 전역 탐색 어댑터를 추가한다.

### 배경

- toe 보정이 저장소 전체에 없다(`toe` grep 0건). ASTM E8/D638의 toe correction은 인장 전처리 표준 단계다. 현재는 `curve.crop` / `curve.scale_shift` 수동 우회뿐이다.
- 최적화는 `scipy.optimize.least_squares(method="trf")` 단일이며 `OptimizerAdapter` Protocol 경계가 이미 있다(`modeling/domain/reference_voce_calibration.py:438`). `multistart(1-32)`로 국소해를 완화 중이다.

### 작업

1. `metal.toe_compensation` 메서드 추가. 방식 파라미터 = `linear_extrapolation`(탄성 직선 역외삽 원점 이동) | `offset_shift`(지정 변형률 이동) | `none`. 적용 구간·기준(응력 하한/상한 또는 수동)을 숨은 기본값 없이 명시한다. 결과는 새 revision, 원본 불변.
2. Process 화면에서 보정 전/후 곡선 비교 표시.
3. 선택(별도 커밋): `DifferentialEvolutionOptimizerAdapter`. 기존 Protocol 구현, seed 고정 결정성, bound 필수, Scientific Profile에서 optimizer 선택 노출. 기존 `trf` 대비 회귀 없음을 픽스처로 증명한다.

### 완료 기준

- toe가 있는 synthetic 곡선 픽스처에서 보정 후 원점 정렬과 탄성계수 recovery가 검증된다.
- 보정 파라미터가 레시피에 보존되고 재실행 시 동일 결과(결정성)를 낸다.

### 제외 범위

- 압축/굽힘 시험 toe
- 자동 toe 감지 휴리스틱(1차는 명시 파라미터만)
