> 작성: 2026-08-06

## 1. 배경과 목표

GRANTA MI 기반으로 운영해 온 소재 물성 DB(소재 메타 -> 시험 데이터 -> 프로세싱 데이터 -> 솔버 카드의 링크 구조)를 외부에서 개발 중인 오픈소스 플랫폼 위에 재구축한다.

사내 제약(외부 저장소 push/PR 불가, WSL·Docker Desktop 사용 불가)에 따라 다음 두 업무를 병행한다.

1. **요구사항 트랙:** 전체 기획과 오픈소스에 요청할 요구사항을 구체 문서(에이전틱 코딩용 패킷)로 작성·등록하고 반영분을 재검토한다.
2. **검증 트랙:** 내부 저장소에서 빌드하고 사내 데이터 구조를 적용해 실데이터로 테스트한다.

**핵심 원칙:** 이미 구축한 사내 데이터 형식(JSON 스키마)이 기준이다. 인하우스 프로세싱/카드 생성 코드는 고수하지 않고 플랫폼 기능으로 대체할 수 있지만, 형식과 링크 구조·추적성은 유지한다.

## 2. 오픈소스 적합성 평가(요약)

FastAPI + React + PostgreSQL 16 기반 모듈러 모놀리스다. 계약 우선(JSON Schema draft 2020-12, 108개), 불변 리비전 + SHA-256 계보, fail-closed 설계다. 상세 근거는 `05_갭분석_상세.md`에 정리한다.

| 사내 요구 | 판정 | 요지 |
| --- | --- | --- |
| 3.1 유연한 DB 형식 정의 | 부분 충족 | `Database -> Profile -> Table -> Attribute/Layout/Subset/LinkType` 런타임 정의(`draft -> validate -> publish`)는 GRANTA 개념과 1:1 대응하며 동작한다. 단, JSON 번들 일괄 세팅 기능이 없고 `x-` 확장을 해석하지 않으며 곡선 채널 메타가 없다. -> P1-P3 요구 |
| 3.1 링크 구조(원천 -> 프로세싱 -> 카드) | 충족 | exact-revision `RecordLink` + `Workflow Explorer`(양방향 BFS)로 계보 추적이 가능하다. 데모 시드가 `Material -> Test -> Processing -> IR -> Neutral -> Card` 7단계 체인을 실제 구성한다. |
| 3.3 중립 데이터가 시험별인가 | 아님(확인됨) | 중립 포맷은 단일 봉투 + 모델 패밀리 3종(탄소성 tabulated/일반화 Maxwell/초탄성) `oneOf`다. DMA는 전단완화 Dataset으로 우회하며 FLD류는 부재한다. -> P4로 시험별 커버리지 확장 요구. 사내 "시험별 프로세싱 데이터"는 카탈로그 테이블(`elastoplasticity` 등)로 표현하고 모델 패밀리 IR과 링크로 연결하는 이원 구조가 적합하다. |
| 3.2 인증(승인)/리뷰/리비전 | 리비전·리뷰 커널 충족, 운영 공백 | append-only 리비전(+사유 필수, `latest` 별칭 거부), 리뷰(SoD, digest 고정), Release(`supersede`/`withdraw`)는 견고하다. 그러나 리뷰 대상이 Material/카드뿐이고 업로드 승인이 없다(-> P7). 승인 -> DB 공개가 미완(#160), audit 기록이 사실상 미배선(-> P9), 웹 로그인도 부재한다(-> P8). |
| 3.2 권한별 업로드(import/수기) | 부분 충족 | 단건/다건 등록, CSV/XLSX governed import, ETag 수정 리비전을 모두 구현했다. 단, 역할 preset 3종 고정이 사내 3역할 정의와 불일치한다(일반 사용자에 프로세싱 권한이 고정 포함되고 시험 Run 생성은 불가). -> P7 |
| 3.4 환경(비WSL/비Docker Desktop) | 해결 가능 | 공식 경로는 Docker Desktop + WSL이지만, (a) Hyper-V Ubuntu VM + Docker Engine(무료, Apache-2.0)이 이슈 #162로 이미 계획됐고, (b) Windows 네이티브 실행도 구조적으로 가능하다(PG16 extension 불필요, 비컨테이너 실행 명령 문서화). |
| 프로세싱(탄소성·점탄성) | 대등 이상 | smoothing 3종, 탄성계수 5방식, true 변환, 네킹, 경화 4식(+블렌딩), Prony+BIC, DMA 동시 피팅, TTS, 초탄성 4식, holdout을 지원한다. 결손은 toe 보정(P10)과 전역 최적화(DE, 선택)다. |
| 통계(분포·envelope) | 미충족 | 평균/SD/CI/이상치까지만 지원한다. Normal/Weibull/Lognormal 피팅과 상·하위 5% envelope가 없다. -> P5 |
| 솔버 카드 | 미충족(방식 상이) | Abaqus/OpenRadioss를 Python f-string으로 하드코딩했고 단위계는 kg-m-s 단일이다. LS-DYNA/Optistruct/Ansys와 템플릿/Template Designer가 없다. -> P6. 단, Mapping Report의 preview-digest 검증은 사내 방식보다 우수하므로 유지한다. |

**종합:** 골격(카탈로그·거버넌스·계보)은 사내 요구와 방향이 정확히 일치하고 품질이 높다. "딱 맞지 않아도 베이스가 잡힌 코드"라는 판단은 타당하며, 채택 후 요구사항 반영으로 보완하는 전략이 성립한다. 실질 블로커는 스키마 번들 import, 로그인, 업로드 승인, 통계, 카드 템플릿 5가지로 명확하다.

## 7. 플랫폼 방향성 검토

### 7.1 외부 로드맵 판독

이슈·backlog·roadmap 문서 기준으로 UX 기준 확정(#167) -> 데모 복구(#157) -> Materials(#159) -> Modeling Data/Process(#158 일부)가 완료됐다. 현재 금속 탄소성 Fit 구현(3B)이 진행 중이다. 이후 `Export -> #160(승인·공개) -> #161 -> #184(UI 정리) -> #162(Hyper-V VM + NIST 실측 E2E 최종 게이트)` 순서다. 폴리머(#195)·엘라스토머(#196) Fit은 기획 게이트 후 착수 예정이다. 운영은 "이슈 1개 = Codex 작업 단위, backlog 단일 진실, 순차 실행"의 엄격한 에이전틱 개발 체계다.

### 7.2 독자 제언(사내 관점)

1. **데이터 기반 우선:** 사내 가치의 원천은 축적된 형식·데이터다. P1(번들 import)·P3(단위)가 반영되어야 이관이 시작되므로 최우선 협의 대상으로 삼는다.
2. **거버넌스는 재사용, 재발명 금지:** 리비전·리뷰·계보 커널은 GRANTA보다 정교하다. 사내 인증 체계(승인/리뷰/리비전) 요구는 이 커널 위 확장(P7·P9)으로 충분하며 별도 시스템을 만들지 않는다.
3. **솔버 카드는 템플릿 생태계로:** 사내 Jinja2 템플릿 자산 경험을 P6에 반영해 "코드 수정 없는 신규 카드"를 표준화하면 사업부별 솔버(LS-DYNA/Optistruct/Ansys) 확장을 사내가 직접 수행할 수 있다. 외부 의존 최소화의 핵심이다.
4. **플러그인 계약 주시:** `solver_exporter` 등 7종 확장 계약이 이미 예약돼 있다. 장기적으로 사내 고유 프로세싱(예: 특수 시험)을 플러그인으로 이식하면 upstream과의 결합을 줄일 수 있다.
5. **통계 신뢰성 확보:** P5는 대표값 문화(승인된 mean/±5%)의 전제다. 반영 전까지 대표값 산출은 인하우스 코드 병행을 유지한다.
6. **리스크 관리:** 단일 메인테이너 저장소(버스 팩터), `non_production` 상수, 문서-코드 불일치(리뷰 상태 모델 등)가 있다. 내부 미러와 버전 고정으로 공급 연속성을 확보하고 도입 판정(M5)에 "upstream 중단 시 자체 유지보수 가능성" 항목을 포함한다.
