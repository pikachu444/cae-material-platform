# 재설계 반영 평가와 다음 구현

2026-09-07 · 세 단계 로컬 체크포인트의 평가. 시안은 아직 확정하지 않았다.

**개편을 막던 주요 정책은 정리했고, 여섯 시안에 목록 선택·미리보기·전체 상세 동작을 반영했다.
그러나 처음 요청한 재설계 전체를 완료했다고 평가할 수는 없다.** 실제 API 연결과 저장 정책 변경,
등록·처리·모델링 화면, 공학적 검증과 서비스 전환이 남아 있다. 이번 커밋은 그 작업을 이어갈 기반이다.

## 화면에서 달라진 점

- 처음에는 목록을 넓게 읽는다. 이름에 조건을 몰아넣지 않고 소재·시편·시험·온도·속도를 나눈다.
- 한 번 선택하면 미리보기가 나타난다. 접으면 선택은 유지된다. 큰 화면의 일부 안은 오른쪽,
  다른 안과 좁은 화면은 아래에 열린다. 아래 미리보기의 제목과 행동은 화면 안으로 이동하지만,
  곡선과 모든 조건을 보려면 세로 스크롤이 필요할 수 있다.
- 더블클릭, Enter 또는 ‘상세 열기’로 목록을 치우고 해당 자료에 집중한다.
  돌아오면 검색·페이지·목록 스크롤·선택과 키보드 초점을 복원한다.
- 기존 카드는 직접 찾고 저장 파일을 내려받는다. 처리나 생성을 다시 시키지 않는다.
  물성값은 물성명·값·단위별로 표시한다. 적용 조건이 없으면 ‘미기재’라고 표시한다.

이는 `workspaces.html`의 합성 데이터 시안 동작이다. `apps/web-next`는 앞서 만든 별도 React
기반 초안이며, 여섯 시안이 이미 React에 이식되었거나 실제 데이터와 연결됐다는 뜻이 아니다.

## 처음 요청한 일곱 결과물의 충족도

| 요청 | 현재 반영 | 아직 필요한 일 |
| --- | --- | --- |
| 1. 실제 frontend 진단 | [프로그램 §2](../../docs/planning/frontend-redesign-program.md#2-current-diagnosis-evidence)에 코드 크기·상태·CSS·저장 방어·빌드 기준과 화면 근거를 정리했다. | 대표 업무의 현재 사용 시간·반복 조작·실데이터 응답성을 측정해야 한다. 모든 기존 업무를 실행 검증한 것은 아니다. |
| 2. 업무·보존·교체 대응 | 프로그램 §3에 조회, 카드, 업로드, 처리, Fit, 관리 업무의 대응을 두었다. 공학 로직과 API 보존, 화면 구조 교체를 구분했다. | frontend 계산·검증·출력 조합 로직의 전수 목록과 회귀 기준은 추출 단위별로 보강해야 한다. |
| 3. UX·IA·비교 시안 | 직접 조회 경로, 좌측 진입점, 조건 열, 개별 물성값, 선택/미리보기/상세, 여섯 독립 비교안을 제공한다. | 등록·처리·생성의 기본/고급 설정 화면은 새 구조로 아직 구현하지 않았다. 시각적 최종 승인도 열려 있다. |
| 4. 전략·architecture | 기존 유지/부분 교체/새 foundation 전략과 추천안, 소유권·상태·CSS·검증·확장 방향을 프로그램과 architecture에 기록했다. 새 React 초안을 분리했다. | 후보별 실제 대량 표·곡선 성능, 키보드/접근성, 유지보수와 라이선스 검토를 완결하고 선택할 필요가 있다. 설치됐다는 이유로 최종 채택하지 않는다. |
| 5. governance 변경 | ADR-0036/0037, 재료만 리비전 관리, 새 기반 허용, 기존 시각 정책의 고정 권한 해제, 위험에 따른 검사 범위를 반영했다. 과거 ADR에는 대체 관계를 남겼다. | 이후 실제 계약·마이그레이션·선택 시안에 맞춘 최종 규칙 정리가 남는다. |
| 6. 구현·전환 계획 | RD-00~07로 foundation → 연결된 대표 업무 → 검증 → 쓰기/확장 → 일괄 전환 → 구형 제거 순서를 명시했다. | 실제 연결·전환·복구 리허설은 아직 실행하지 않았다. |
| 7. 검증 가능한 acceptance | 시안의 선택·키보드·페이지 복귀·빈 결과·미등록 파일·정확한 다운로드를 브라우저에서 검사했다. 공학/저장/복구 기준은 프로그램에 분리했다. | 실데이터, 합의된 공학 기준과 허용오차, 비동기 실패·stale·미저장 이탈, 사용성 측정, 실제 모니터 검증이 필요하다. |

최초 요청의 방향은 계획에 반영했지만 분석과 검증의 깊이까지 모두 충족한 상태는 아니다.
누락을 숨기거나 정적 시안 통과를 전체 제품 완료로 취급하지 않는다.

## 공학 서비스로서 반드시 이어갈 자산

재료만 수정 이력을 관리한다는 결정은 확정이다. 다른 데이터의 이름 수정에 별도 리비전·사유·증빙
입력을 다시 요구하지 않는다. ID로 연결된 소재·시편·시험·모델·카드 관계와 저장 결과가 사용한
입력·설정은 유지한다. 이 정책은 문서에 반영됐고 DB/API의 실제 변경은 후속 구현이다.

원본 파일 보존은 모든 편집을 기록하는 것과 다르다. 업로드한 원본, 처리 결과, 저장된 카드 파일을
서로 덮어쓰지 않고 구분하는 것이다. 처리 데이터 다운로드와 솔버 카드 추출도 다른 산출물이다.
지원 형식·자동 처리·기본값은 기존 계약과 검증된 로직을 기준으로 정하며 임의로 확대하지 않는다.

UI를 버릴 때 함께 버리면 안 되는 예는 `apps/web/src/curve-contract.ts`의 값 변환
`value * scale + offset`과 편차의 scale-only 변환, `features/modeling/model/processing-registry.ts`의
처리 설정/검증, 기존 plotting·Fit·DMA·Prony와 세션 전이이다. 실제 추출 전에 기준 입력과 기대 결과를
고정하되, 잘못된 기존 동작을 정답으로 삼지는 않는다.

서버 데이터는 query key에 실제 입력 ID·필터·조건을 포함한다. URL은 탐색/검색/페이지를 소유하고,
편집 초안은 feature form, 열림·접힘은 임시 UI 상태가 소유한다. 비동기 결과는 실행 입력과 요청에
귀속시킨다. 이름 변경은 결과를 무효화하지 않으며, 계산 입력 변경은 이전 결과를 현재 결과처럼
보이지 않게 한다. 현재 정적 시안은 이 비동기·미저장 정책을 검증하는 도구가 아니다.

예를 들어 DMA 시험에 새 온도 조건이 추가되면 API 스키마/adapter, 해당 조건 필드와 검증,
처리 registry, query key와 곡선/결과 검증을 바꾼다. Button·Dialog·좌측 메뉴·다른 시험 화면을
같이 고치는 구조로 만들지 않는다. 실제 지원 범위를 먼저 확인한다.

## 스킬 평가

**모든 스킬을 매번 적용할 필요는 없다. 작업 방법을 돕는 도구로 남기고 제품 요구의 중복 권한을 줄이는 것이 낫다.**

| 스킬 | 판단 | 적용 범위와 이번 정리 |
| --- | --- | --- |
| frontend-ui-engineering | 유지 | 실제 React/CSS 구현의 접근성·상태·기본 품질. 라이브러리나 기존 모습을 고정하지 않는다. |
| webapp-testing | 유지 | 실제 브라우저 행동과 캡처. 단순 문서 변경에는 적용하지 않는다. |
| material-platform-frontend-architecture | 조건부 유지 | 소유권·feature 간 상태·API/domain 경계·hotspot 변경에만 적용한다. 남아 있던 A/B 전제, brownfield 선행 강제, 사소한 스타일에도 architecture packet을 요구하는 문구를 이번에 수정했다. |
| desktop-engineering-ui | 조건부 유지 | 공학 정보 배치와 전체 화면 비교에 가치가 있다. 검사 규모는 visual matrix가 기준이며 작은 수정마다 전 해상도/거대 검수 절차를 반복하지 않는다. architecture 호출 범위도 맞췄다. |
| web-design-guidelines | 선택적 사용 | 별도 접근성/일반 웹 감사에 유용하다. 공학 업무 이해와 제품 검수를 대체하지 않는다. 모든 작업의 필수 관문일 필요는 없다. |
| 개인 orchestration | 제한적으로 유지 | 작업 경계·기록·커밋/게시 권한을 관리한다. 제품 시각 정책의 주인이 아니다. 이번처럼 Main 직접 구현 요청을 우선하며 사소한 수정에 다중 에이전트를 강제하지 않는다. |
| visualize / PDF / skill-creator | 산출물별 사용 | 시안 비교, 보고서 렌더링, 스킬 편집에만 사용한다. production frontend 의존성이나 상시 개발 규칙으로 확대하지 않는다. |

실제 문제는 스킬의 존재 자체보다 중복되는 지시, 낡은 시안의 권위, 작은 피드백에만 집중한
작업 방식이었다. root/apps 지침과 architecture/visual 스킬의 호출 조건을 함께 맞췄다.
기준 문서는 프로그램(범위/결정), 데이터 정책(domain), architecture(소유권), UI principles(표현),
visual matrix(검사)로 나누고 스킬은 실행 절차만 맡긴다.

맥락 유지는 [버전 관리되는 현재 상태](../../docs/planning/frontend-redesign-status.md)와 프로그램의
누적 요구를 먼저 읽는 방식으로 보완했다. 5분마다 혼잣말하는 자동화는 만들지 않았다.
체크포인트는 완료 증거와 남은 일을 함께 기록하며, 다음 지적을 고칠 때 전체 요구를 다시 대조한다.

## 검증과 다음 판단

현재 시안은 합성 시험 48건/카드 메타데이터 8건, 정확한 카드 예시 파일 1개를 사용한다.
브라우저 검사 230개와 66개 캡처는 이 범위의 결과다. 실제 데이터 규모나 작업 시간 성능 목표는 아니다.
React 초안 18개 테스트, typecheck, prototype 및 일반 build도 통과했다. 일반 build의 gateway는
연결되지 않았음을 명확히 반환한다. 기존 서비스는 전환하지 않았다.

다음 우선순위는 ① 조회 기본 화면과 비교 작업 화면의 선택 ② 실제 인증/API를 통한
실험 조회→관련 저장 카드→다운로드 ③ 오류·저장·입력 변경과 과학 결과 검증 ④ 등록/처리/모델링 확장이다.
주 사용 화면 크기·실제 데이터 규모와 공학 기준/허용오차는 검증 전에 결정해야 한다.
수치 성능 목표는 기존 대표 업무를 측정한 뒤 제안한다.

전환 전 계약·동작·시각 검증과 복구 리허설을 통과해야 한다. 구형 코드/CSS/dependency는
소비자가 없고 기능 대응·대체 경로가 확인된 뒤 삭제한다. 전환 실패 시 이전 배포 산출물로
되돌릴 수 있어야 하며 DB 데이터 삭제나 되돌릴 수 없는 마이그레이션을 복구 수단으로 사용하지 않는다.
