# 다음 설계 작업과 저장소 정리 검토

작성: 2026-09-07. 상태: 사용자 검토용 제안. 제품 코드·운영 설정·기존 규칙을 변경하거나 시안을 확정한 결과가 아니다.

## 먼저 볼 내용

**이 태스크에서 설계와 규칙 검토를 정리하고, 대표 화면을 확인한 뒤 구현을 작업 단위별로 이어간다.**
기존 전체 개편 계획은 유지한다. 소재 중심 탐색, 카드·표 전환, 반복 실험 통계를 그 계획 안에 반영한다.
여섯 시안을 다시 모두 제작하거나 거대한 공통 기반부터 만드는 단계로 돌아가지 않는다.

추천하는 다음 순서는 다음과 같다.

1. 소재 중심 탐색의 대표 화면을 만든다. 좌측 트리·필터, 중앙 카드/표, 오른쪽 미리보기와 상세 확대를 같은 자료로 확인한다.
2. 사용자가 화면 방향을 선택하는 동안 저장소 정리 변경안을 준비한다. 화면 선택과 규칙 변경은 각각 무엇을 승인하는지 구분한다.
3. 승인한 규칙을 정리하고, 실제 API에 연결한 조회·다운로드 업무를 구현한다.
4. 조회 업무를 검증한 뒤 실험 등록·처리·반복 통계·결과 저장을 연결한다.
5. 나머지 모델·솔버·관리 업무를 확장하고, 검증 후 한 번에 전환한다.

현재까지는 로컬 3개 커밋과 후속 Granta 수정이 있다. 새 frontend는 실제 API에 연결되지 않았다.
이번 검토는 [전체 프로그램](../../docs/planning/frontend-redesign-program.md)의 RD-01에 속한다.
RD-00의 과거 정리 완료를 취소하지 않되, 아래에서 발견한 잔여 충돌을 모두 해결했다고 해석하지 않는다.

## 1. 다음 대표 화면의 작업 범위

### 기본 구성

| 영역 | 제안하는 역할 |
| --- | --- |
| 좌측 업무 메뉴 | 소재·데이터 탐색, 등록, 처리·분석의 진입점. 세부 메뉴명은 대표 화면에서 확인한다. |
| 탐색 영역 좌측 | 실제로 펼치고 접는 소재 분류 트리와 별도의 조건 필터. 선택한 소재의 시편·실험 연결도 탐색할 수 있게 한다. |
| 중앙 | 소재는 주요 물성을 정렬한 카드가 기본. 실험은 온도·속도·방향·시편·상태를 별도 열로 비교하는 표가 기본. 두 보기를 전환할 수 있다. |
| 오른쪽 | 선택 항목의 미리보기. 소재를 선택하면 기본 물성, 관련 실험, 처리 데이터·모델, 통계, 솔버 카드에 접근한다. |
| 확대 상세 | 중앙 목록을 감추고 선택한 자료를 넓게 본다. 목록 복귀 시 검색조건·페이지·스크롤·선택·키보드 초점을 복원한다. |

소재를 고르는 절차를 모든 업무의 필수 첫 단계로 만들지 않는다. 전체 실험 검색과 기존 솔버 카드 검색·다운로드는 직접 진입한다.
소재에 연결된 데이터를 보여주는 것은 화면의 탐색 방식이다. 여러 entity를 하나로 합치거나 관계를 일대일로 바꾸지 않는다.
기존 결과 조회와 다운로드에 처리·모델 생성·카드 생성을 다시 요구하지 않는다.

소재 카드는 소개용 이미지나 줄글 대신 항목·수치·단위를 정렬한다. 같은 분류에서는 핵심 항목의 위치를 맞추고,
조건부 물성에는 온도·방향 등 필요한 조건을 붙인다. 조건이 여러 개면 임의의 대표값을 만들지 않는다.
표/카드 전환은 보기만 바꾸고 검색 결과·페이지·선택을 유지한다. 필터/정렬/페이지 변경으로 선택을 해제하는 경우에는
미리보기도 함께 정리하고 첫 항목을 자동 선택하지 않는다. 상세 복귀는 이와 별개의 복원 동작이다.

검토용 대표 상태는 다음 여섯 개면 충분하다. 기존 여섯 서비스 시안의 전면 재제작을 뜻하지 않는다.

- 소재 카드 목록과 오른쪽 미리보기
- 같은 소재 결과의 표 보기
- 소재에 연결된 실험 목록과 곡선 미리보기
- 확대 상세와 원래 목록으로 돌아오기
- 전체 실험 또는 솔버 카드로 직접 진입하기
- 긴 이름·여러 조건·다음 페이지·빈 결과·불러오기 실패

데스크톱에서는 목록 옆의 오른쪽 미리보기가 실제로 유지되는지 확인한다. 좁은 작업 영역에서의 전환은 명시적으로 설계하고,
임의로 목록 아래에 미리보기를 붙이지 않는다. 첫 공통 화면은 기존 다섯 CSS viewport에서 검증하되,
실제 장비 가독성이나 데이터 규모별 응답성을 합성 자료로 입증했다고 주장하지 않는다.

근거: 초기 기획을 추출한 [스키마 정의](../../docs/00-research/schema-driven-integration-source/03_스키마_정의_세트.md)는
Technical Data를 중심 허브로 두며 실험·처리·통계와 다중 관계를 가진다.
[Altair 공식 화면 안내](https://help.altair.com/altairone/topics/materialsdb/tutorial_amdc_interface_r.htm)는 소재별 타일과 오른쪽 정보·물성·곡선·CAE 모델 패널을 설명한다.
[표 설정 안내](https://help.altair.com/altairone/topics/materialsdb/table_view_tailor_r.htm)는 카드/표 전환과 물성 열 선택을 제공한다.
이것은 우리 탐색 설계의 참고이며 Altair의 데이터 구조나 알고리즘을 그대로 채택한다는 뜻이 아니다.

### 처리·통계는 두 번째 연결 업무로 준비

실험 선택 → 개별 처리 → 필요 시 반복 실험 정렬·통계 → 결과 확인·저장·다운로드를 하나의 업무로 만든다.
모델과 솔버 카드 생성은 저장된 처리·통계 결과에서 이어지는 선택 업무다. 처리 데이터 다운로드와 카드 추출은 별도 행동이다.

초기 통계 제안은 비교 가능한 조건의 단조 인장 반복시험이다. 독립 표본은 측정점이 아니라 시편/시험이며,
각 실험을 동일한 비중으로 다룬다. 단위와 응력·변형률 의미를 맞춘 뒤 관측 공통 구간에 선형 보간하고 외삽하지 않는다.
평균·표준편차·최소·최대와 기여 시편 수를 제공한다. 조기 파단은 감추거나 0으로 채우지 않고 파단 변형률 통계로도 남긴다.
관측 최솟값, 평균의 신뢰구간, 설계에 사용하는 통계적 하한은 구분한다.

현재 [공통 처리 통계](../../backend/src/cmp/modules/processing/domain/common_ensemble.py)는 공통 구간 선형 보간,
평균·중앙값·표준편차와 정규근사 신뢰구간을 구현한다.
[인장 반복 통계](../../backend/src/cmp/modules/statistics/domain/reference_tensile_replicates.py)는 이미 일치하는 격자를 요구하며
최소·최대와 Student-t 평균 신뢰구간 등을 계산한다. 두 경로의 통계 가정과 저장/API 범위를 먼저 대조한다.
새로운 통계 기능을 전부 처음부터 만드는 계획도, 기존 계산을 무검증으로 정답 처리하는 계획도 아니다.
적은 시편 수에서 하위 5% 곡선을 곧바로 설계 허용값으로 제공하지 않는다.
[NIST 구간 해석 안내](https://www.itl.nist.gov/div898/handbook/prc/section2/prc263.htm)를 참고해 통계 정의와 검증 자료를 합의한다.

Material 정보 수정만 리비전 이력을 남긴다는 결정은 유지한다. 통계 결과는 사용자가 저장한 독립 결과이며,
입력 실험과 실제 처리 설정을 연결한다. 매번 미리보기하거나 이름을 바꿀 때 변경 사유와 새 리비전을 요구하지 않는다.
raw 업로드·지정 양식·처리 기본값의 지원 범위는 다음 연결 작업에서 API/기준 파일로 확인하며 새 형식을 추측하지 않는다.

## 2. 실제로 발견한 저장소 문제

검토 대상은 redesign worktree의 활성 진입 문서, 관련 ADR·T/Q 참조, 5개 frontend skill, hook/guard 진입 코드,
개인 Codex 설정과 이 프로젝트용 오케스트레이션이다. 모든 과거 T 작업이나 전체 backend의 재검증을 완료한 것은 아니다.

| 문서 분류가 현재 규범과 과거 결정을 구별하기 어려움 | `documentation-manifest.yaml`은 ADR·planning·analysis 전반을 authoritative로 분류 | 제안·현재 결정·구현 사실·과거 기록을 구분한다. 파일 분류만으로 모든 문장을 현재 의무로 만들지 않는다. |
| 상태를 여러 곳에서 따로 적어 불일치 | backlog는 RD-00 in progress, program/status는 완료 | 진행 상태는 checkpoint 한 곳에서 관리하고 backlog·program은 링크한다. 이 검토에서 backlog의 링크와 이전 상태를 정리한다. |
| frontend guard가 구형 앱에만 적용 | `scripts/check_frontend_guard.mjs`의 SOURCE_ROOT는 `apps/web/src`; 루트 `npm run check`도 web-next 검증을 포함하지 않음 | 새 앱의 의존 방향·타입·동작 검사를 명시한다. 구형 selector·hotspot 예외표를 새 앱에 복제하지 않는다. |
| 문서 검사에 과거 이슈별 예외가 누적 | `documentation_impact.py` 5,950줄에 #298/#331/#351 등의 특정 경로·해시·삭제 집합 분기 | 검사 통째 삭제가 아니라 공통 유효성 검사와 과거 evidence 보존 검사를 분리한다. 승인된 구형 삭제가 현재 기능 변경을 막지 않게 한다. |

T 번호는 과거 구현 작업을 찾는 표식이며, 그 자체가 현재 제품 요구나 모든 변경의 실행 순서가 아니다.
예를 들어 T-53은 공통 처리, T-85/T-86은 그 UI, T-91은 당시 탐색 구현을 가리킨다.
`product-capability-map.md`와 `test-strategy.md`에서 관련 코드·시험을 찾는 데 사용하되,
과거 exact-revision 화면이나 당시 3-pane 구성을 새 제품의 정답으로 복사하지 않는다.

## 3. AGENTS·skill·오케스트레이션 판단

**AGENTS.md는 짧은 작업 안내로 유지하고, skill은 반복해서 도움이 되는 절차만 남기는 것을 추천한다.**
둘 다 많을수록 좋은 것은 아니다. 모델 이름을 바꾸거나 지침을 전부 없애는 것만으로 결과가 좋아진다고 보장할 수 없다.

| 대상 | 제안 |
| --- | --- |
| root AGENTS | 실행·검증 명령, 변경 보존, 현재 계획 입구, 핵심 공학/보안 조건, 작업 완료 조건만 둔다. UI 스타일·과거 이슈·agent 모델표는 옮긴다. |
| apps/web/AGENTS | 구형 앱 유지·이관에 필요한 차이만 남긴다. 새 앱의 기본 지침으로 읽히지 않게 한다. |
| apps/web-next | 현재 별도 AGENTS 없음. root와 frontend architecture로 충분한지 먼저 확인한다. 추가한다면 실제 실행 명령과 해당 앱의 차이만 적는다. |
| frontend-ui-engineering | 유지하되 짧게 정리. component·상태·접근성·API 연결 작업에 사용한다. 공통 규칙을 중복하지 않는다. |
| desktop-engineering-ui | 시각 검증 절차와 캡처 도구만 유지. 여섯 시안·과거 이슈·publication 지시를 반복하지 않는다. |
| material-platform-frontend-architecture | 소유권·API·상태 경계가 바뀌는 작업에만 적용. 상위 architecture 문서와 중복되므로 짧은 읽기 안내로 축소하거나 필요성이 없으면 통합한다. |
| webapp-testing | 기존 도구 사용법을 유지하되 Python만 우선하는 지시와 source 열람 금지를 재검토한다. 설치된 Node Playwright를 함께 지원하고, 무조건 networkidle을 요구하지 않는다. |
| web-design-guidelines | 선택적인 외부 점검 자료로 유지하거나 프로젝트 skill에서 제거 가능. 매 검수마다 외부 규칙을 새 의무로 가져오지 않는다. |
| 한국어 윤문 도구 | 의미 보존을 위한 선택 도구. 매 문서에 다중 agent 윤문을 강제하지 않는다. 명확한 한국어를 직접 쓰는 것이 기본이다. |

개인 설정에서 확인한 값은 `gpt-6-astra / medium`이다. 반면 개인 프로젝트 orchestration skill은 Fast에
`gpt-5.6-sol/high`, Balanced·Full에 `gpt-5.6-sol/xhigh`를 지정한다. 실제 `cae-full.config.toml`은
Sol/medium이므로 지침과도 다르다. 이 파일의 값이 현재 Desktop 태스크의 실제 추론 설정을 입증하지는 않는다.
프로필 적용을 위해 이 태스크의 모델을 바꾸지 않았다.

추천은 사용자가 선택한 Astra를 Main으로 유지하고, 단순 변경은 Main 단독, 독립 검토가 유용하면 읽기 전용 검수 1개를
쓰는 방식이다. 독립 조사나 격리된 구현이 실제로 도움이 될 때만 별도 작업을 나눈다. 현재 Full의
요구 감사→Luna 구현→검수→교정 agent 고정 순서는 필수 기본값에서 제외하는 안을 제안한다.
최대 동시 agent 수 12는 한도이며 실제 12개를 실행하라는 설정은 아니다.

오케스트레이션에서 유지할 것은 한 checkout의 동시 작성 충돌 방지, Main의 요구 해석 책임, 결과 근거 확인,
실패 원인을 고친 뒤 관련 검사만 다시 실행하는 원칙이다. 규칙 불일치 때문에 정상적인 분석을 중단하거나
사용자가 원한 Main 직접 작업을 자동으로 다른 모델에 넘기는 동작은 없애야 한다.

### 자동 검사와 hook

저장소에는 `.codex/config.toml`이 없고 `.codex/hooks.json`이 있다. agent 모델/역할 설정은 개인 Codex 디렉터리에 있다.
`.githooks/pre-push`는 자동 LLM 검수가 아닌 결정적 검사 파이프라인을 호출하며, 현재 `core.hooksPath`도 `.githooks`다.
Codex PreToolUse도 publication 파이프라인을 호출하므로 같은 push에서 검사가 중복될 가능성은 있다.
실제 hook 이벤트·신뢰 상태·중복 실행 횟수는 이번 정적 검토로 입증하지 않았다.

`^Bash$` matcher는 공식 hook 예시에도 쓰이므로, 화면상 도구명이 exec_command라는 이유만으로 고장이라고 판단하지 않는다.
개인·프로젝트·plugin hook은 함께 실행될 수 있으므로 후속 정리에서 실제 활성 소스를 확인한다.
Stop hook의 문서 검사는 사용자 질문에 답하거나 작업을 인계하는 것까지 방해하지 않는지 점검한다.
코드/문서가 바뀌지 않은 반복 턴에는 같은 검사를 재실행하지 않는 안을 검토한다.
검증 결과 재사용은 변경 내용과 설정이 같을 때로 제한하고, 무조건 통과시키는 우회는 만들지 않는다.

## 4. 공식 문서를 적용하는 방식

2026-09-07 공식 문서 확인 결과다. API 모델 설정을 Desktop에 그대로 옮기지는 않는다.

- [Astra 모델 가이드](https://developers.openai.com/api/docs/guides/latest-model): skill/AGENTS 충돌 점검, 자율 진행 범위 명시, 응답 문체 조정, 작업에 맞춘 검증을 권고한다. 이번 지침 정리 방향을 뒷받침하지만 특정 저장소 구조의 성능을 보장하지 않는다.
- [Codex 권장 사용법](https://learn.chatgpt.com/guides/best-practices): 짧고 정확한 AGENTS, 반복 작업에 한정한 skill, 일관된 작업 단위별 대화를 권고한다. 복잡한 목표에는 계획과 완료 조건을 제공한다.
- [AGENTS 적용 방식](https://learn.chatgpt.com/docs/agent-configuration/agents-md): 전역과 디렉터리별 지침이 합쳐진다. 중복·충돌을 실제 읽기 경로에서 점검해야 한다. 기본 32KiB 설명은 이 태스크에서 지침이 잘렸다는 증거가 아니다.
- [공식 hook 안내](https://learn.chatgpt.com/ko-KR/docs/hooks): 일치하는 여러 hook은 함께 적용될 수 있고 프로젝트 hook은 신뢰 상태의 영향을 받는다. 파일 존재만으로 실행 여부를 단정하지 않는다.

### 읽기 쉬운 문서로 정리하는 예

“ordinary-ID read-back / exact association / eligibility invalidation” 대신
“저장한 데이터를 다시 열었을 때 같은 대상이어야 한다. 이름을 바꿔도 연결은 유지한다. 입력을 바꾸면 이전 계산 결과를 현재 결과로 표시하지 않는다.”라고 쓴다.
API 식별자·수학 용어는 필요한 곳에서 원문을 함께 표기한다. 불명확한 말을 쉬운 말로 바꾸다가 공학적 의미를 생략하지 않는다.

기준 문서는 역할별로 하나씩 둔다: 현재 제품 방향은 program, 진행 상태는 checkpoint, 데이터 정책은 data-management-policy,
코드 책임은 frontend-architecture, 화면 원칙은 UI principles, 작업별 검증은 testing 문서, 결정 이유는 ADR이다.
새 번호 체계를 추가하지 않고 기존 문서의 중복을 줄인다. 이 보고서는 승인 전 제안이며 새로운 상위 규칙이 아니다.

## 5. 태스크를 나누는 시점과 재개 방법

지금은 같은 설계 문제를 정리하는 중이므로 이 태스크를 유지한다. 다음 중 하나가 끝나는 시점을 새 태스크 경계로 추천한다.

| 작업 단위 | 끝나는 조건 |
| --- | --- |
| 설계 검토 | 대표 화면과 탐색 동작을 사용자가 선택하고 남은 결정이 정리됨 |
| 저장소 지침 정리 | 승인한 문서·skill·프로필·검사 변경을 적용하고 충돌 및 영향 검증 완료 |
| 실제 조회·다운로드 | 소재 경유와 직접 진입 모두 API 연결·권한·다운로드·복귀·오류 복구 검증 완료 |
| 등록·처리·반복 통계 | 지원 형식 등록부터 처리·통계 저장·재조회·다운로드와 수치 검증 완료 |

새 태스크는 같은 redesign 작업을 이어갈 때 `C:/SourceCodes/cae-material-platform-redesign`과
`codex/frontend-redesign`을 사용해야 한다. main이나 원래 #392 checkout에서 자동으로 다시 시작하면 현재 로컬 수정이 빠진다.
다른 worktree가 필요한 경우 현재 수정까지 어떻게 전달할지 먼저 정한다. 기존 작업을 버리거나 숨기는 방식은 사용하지 않는다.
단순히 대화가 길다는 이유로 전체 기록을 복제하는 fork를 반복하지 않는다.

재개할 때 읽는 것은 [checkpoint](../../docs/planning/frontend-redesign-status.md), program의 현재 범위,
해당 작업 코드·계약·검증 결과다. checkpoint에는 전체 목표, 확정/미확정 사항, 작업 위치, 완료 증거, 바로 다음 행동을 남긴다.
압축·새 피드백·독립 검수 전에는 전체 요구와 변경 범위를 다시 대조한다. 5분마다 알림을 보내는 cron은 만들지 않는다.
이 방법은 기억 상실이 절대 없다는 보장이 아니라, 잘못 이어가도 자료와 실제 코드로 발견·복구할 수 있게 하는 방법이다.

## 6. 이번 변경과 확인 범위

이 보고서와 program/checkpoint/backlog의 진행 안내만 갱신한다. 제품 코드, 시안 HTML/CSS, AGENTS,
ADR, skill, hook, 개인 설정과 dependency는 수정하지 않는다. 앞의 규칙 정리는 실제 변경안을 준비하기 위한 제안이다.
기존 원본 checkout과 미커밋 시안 변경을 보존한다. 새 태스크 생성·commit·push·PR·merge는 수행하지 않는다.

검증 결과: `cmp-check-user-guide` 통과, `cmp-check-doc-impact --mode worktree` 통과,
`git diff --check` 통과. 변경 문서 4개의 로컬 링크 22개를 별도로 확인했고 누락은 없었다.
문서 검사의 210개 변경 파일 집계는 기존 branch 변경을 포함하므로 이번 작업 파일 수가 아니다.
기존 시안 관련 4개 파일의 전후 SHA-256이 같고 원래 #392 checkout은 clean 상태를 유지했다.
이번 변경은 문서 검토이므로 브라우저 캡처, Docker/DB, 수치 정확도와 실제 hook 발동 검증은
수행 대상이 아니다. 후속 구현에서 필요한 검증으로 남긴다.

독립 검수 결과: 사용자 요청 동작과 최종 시안 선택을 혼동할 수 있는 program 문구를 보정한 뒤
이 문서 검토 범위에 대해 `approve`를 받았다. 제품 시각 디자인이나 운영 전환의 승인을 뜻하지 않는다.
